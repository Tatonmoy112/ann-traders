# Operator-reviewed R2 configuration

Environment-specific configuration. The operator applied the localhost CORS policy; this repository has not created buckets or changed their public-access flags.

Create two dedicated buckets. **Staging** must have neither a custom domain nor an r2.dev public URL. **Public images** uses its HTTPS r2.dev URL locally and a custom domain in production. Never grant browser credentials, bucket admin or ACL management. Browser staging PUT capabilities are signed server-side for one generated key with type, length and `If-None-Match: *`; public delivery never permits anonymous writes.

Grant an R2 Object Read & Write token scoped only to the selected staging/public buckets. Keep its Access Key ID/Secret Access Key in server/Edge environment. This application restricts signing to the staging bucket. If organization policy requires separate writer/cleanup credentials, provide the same bucket-restricted interface in those deployments; no browser credential changes are needed.

For localhost use `staging-cors.local.json`, which permits only `http://localhost:3000` and `http://127.0.0.1:3000`, PUT, `content-type,if-none-match`, and ETag exposure. Applying CORS does not make the staging bucket public. For production replace the origin in `staging-cors.example.json` with the exact admin HTTPS origin. Content-Length is generated by the browser and signed, not set by JavaScript. Avoid wildcard origins/headers. Public read CORS, if needed, permits GET/HEAD only.

Configure staging object lifecycle expiration after **one day** as the outage backstop. Do not delete staging objects before the five-minute URL TTL plus the ten-minute safety window. The scheduled outbox consumer performs normal recovery; lifecycle expiration is not a substitute for public-object cleanup. Do not add lifecycle expiry to the public catalog prefix.

Locally set `R2_ENVIRONMENT=development`, loopback `APP_ORIGIN`, `R2_PUBLIC_BASE_URL=https://pub-<actual-id>.r2.dev`, and `R2_CDN_PURGE_MODE=disabled`. Use the real public-bucket URL from its dashboard, never a guessed placeholder. Development writes use `Cache-Control: no-store` and require no CDN purge token. Normal TLS verification remains enabled. Cloudflare r2.dev is rate limited and lacks custom-domain CDN caching; [Cloudflare documentation](https://developers.cloudflare.com/r2/buckets/public-buckets/).

Before production set `R2_ENVIRONMENT=production`, `R2_CDN_PURGE_MODE=cloudflare`, and an HTTPS custom domain, then disable public r2.dev access on the public bucket. Configure restricted zone purge credentials. New production objects use immutable year-long caching and exact-file purge. Existing development objects remain usable with no-store headers; an operator can review metadata/cache policy separately without uploading image bytes again. Output is already sanitized WebP at 320/768/2000px. CDN deletion cannot revoke downloaded bytes.

Pin bucket names per environment. Pending sessions also pin their verification origin and must finish/expire before an origin change. Ready images resolve from stored canonical keys plus the current `R2_PUBLIC_BASE_URL`. Add former trusted origins to `R2_PREVIOUS_PUBLIC_BASE_URLS` for old-session retirement; other origins fail closed. The public projection exposes image/variant keys for consumers. No byte upload or key changes are needed for domain cutover. Production purge must cover every active custom domain; cross-zone migrations require review.

Production acceptance: actual preflight and signed header checks in the supported browsers, wrong-origin/expired/repeated/concurrent PUT tests, oversized and corrupt-file rejection, direct anonymous staging GET denial, immutable Cache-Control on generated objects, exact-file purge after detach, outage/retry/reconciliation, and worker secret enforcement. Do not approve rollout based on provider-double tests alone.
